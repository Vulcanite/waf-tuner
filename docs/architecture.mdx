# Architecture

import Diagram from '@site/src/components/Diagram';

WAF Tuner is an offline false-positive triage tool for ModSecurity and OWASP CRS. A signature can match ordinary application input, such as SQL keywords in a product search. WAF Tuner gives a configured language model the matching rule, the observed value, and application-specific facts so it can explain why the alert may be benign, malicious, or uncertain.

## From the log to a case

1. **ModSecurity writes an audit event.** WAF Tuner tails its JSON Serial log and persists a cursor for restart and rotation.
2. **Ingest stores the event and groups matches.** SQLite holds the audit evidence, cases, and occurrences. A fingerprint groups repeated observations with equivalent match evidence. Score-only rules stay available as context.
3. **A worker analyses a queued match.** It selects the application profile, loads the CRS rule associated with the event, and prepares a bounded copy of the evidence.
4. **The endpoint returns a verdict.** The worker validates the output and records the result on the case. A repair or stronger reasoning call can occur depending on the output and provider settings.
5. **The server checks whether it can draft a rule.** The [review workflow](./review.mdx) explains why some verdicts never produce a draft.

## What the model receives

<Diagram
  name="evidence"
  alt="A worker selects evidence from the audit record, the pinned CRS rule, and the application profile. It redacts and bounds that evidence, sends it to the configured model, and validates the returned verdict."
  caption="Only the selected, bounded evidence is sent to the configured model. SQLite stores the analysis revision."
/>

The initial call uses a system prompt and a JSON evidence message. The evidence can include the method and path, the matched target and value, the rule ID and operator, sibling rule IDs, and the selected stack and route information. Redaction and size limits can remove parts of that evidence. See [data handling](./limits.md#model-egress-and-local-storage) before sending application traffic to a provider.

The response includes a classification, confidence, and the explanation fields `rule_looks_for`, `payload_is`, and `why`. It can also describe uncertainty and the technique’s applicability to the application stack. A technique can be malicious even when it would fail against that stack.

## Where state lives

| Store | Contents |
| --- | --- |
| ModSecurity audit log | Source transactions and detections |
| SQLite | Events, cases, occurrences, profiles, analysis revisions, and drafts |
| Ingest cursor | Audit file identity, read position, and any pending data |
| CRS snapshot or rules directory | The rule text and data files used to interpret matches |

The UI and API operate on this stored state. The operator uses the reviewed output when managing the WAF configuration.
